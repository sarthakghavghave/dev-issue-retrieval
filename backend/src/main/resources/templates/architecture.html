Core Components

Data Layer

Neon PostgreSQL

Cloud-hosted PostgreSQL stores raw GitHub issue records with metadata, labels, comments, and an index_status field (PENDING → INDEXING → INDEXED / FILTERED / FAILED) to track the NLP pipeline lifecycle.

Backend

Spring Boot (Java 21)

Handles GitHub API ingestion on a 6-hour schedule, persists issues to Neon, exposes search and stats REST endpoints, and serves the Thymeleaf web UI deployed on Render.

NLP Service

FastAPI (Python)

Connects directly to Neon to fetch PENDING issues, cleans and filters text, generates embeddings with all-MiniLM-L6-v2, updates the FAISS index, and serves /search with cross-encoder reranking.

Offline / Indexing Pipeline

1. GitHub Ingestion
A Spring scheduler polls the GitHub API every 6 hours for updated issues across Spring Boot, Kafka, Kubernetes, Docker Compose, and PostgreSQL repositories.
↓
2. Neon PostgreSQL Storage
New and updated issues are upserted into Neon with index_status = PENDING. Historical backfill data (~8k issues) also lives here awaiting processing.
↓
3. NLP Preprocessing
The NLP service reads PENDING rows from Neon, cleans HTML/markdown, filters noise (docs, upgrades, duplicates), and sets FILTERED with a filter_reason when applicable.
↓
4. Embedding Generation
Valid issues are encoded with sentence-transformers/all-MiniLM-L6-v2 into normalized dense vectors optimized for free-tier memory limits.
↓
5. FAISS Index Update
Vectors are upserted into an on-disk FAISS IndexIDMap2 with issue metadata in parquet. Status is updated to INDEXED in Neon.

Online / Search Pipeline

1. User Query (Thymeleaf UI)
The developer submits a natural language query through the Spring Boot search page.
↓
2. Spring Boot → FastAPI
The backend forwards the query to the NLP service /search endpoint on Render.
↓
3. Query Embedding
The same MiniLM model encodes the query into a vector for semantic similarity search.
↓
4. FAISS Candidate Retrieval
Top-K similar issue vectors are retrieved from the FAISS index using inner-product similarity.
↓
5. Cross-Encoder Reranking
cross-encoder/ms-marco-TinyBERT-L-2-v2 reranks candidates for precise relevance ordering before results are returned to the UI.

Incremental Ingestion

Periodic GitHub polling

Spring IssueScheduler runs every 6 hours, fetching only issues updated since the last watermark per repository.

Neon as source of truth

All raw issue data lives in Neon PostgreSQL. The NLP service reads PENDING rows in batches — no re-processing of already indexed issues.

Status-driven pipeline

Issues move through PENDING → INDEXING → INDEXED (or FILTERED / FAILED). Filter reasons include forward-port, upgrade, documentation, duplicate, and empty content.

In-place FAISS upsert

New or changed issues replace their vectors in the FAISS index without rebuilding the entire index from scratch.

Architecture Summary

  • Neon PostgreSQL is the cloud database for all raw GitHub issue records and pipeline status tracking.
  • Spring Boot ingests from GitHub on a schedule, serves the web UI, and proxies search requests to the NLP service.
  • FastAPI NLP service preprocesses text, generates embeddings, maintains the FAISS index, and reranks search results.
  • Offline indexing and online search are separated so queries stay fast while the index grows incrementally.
  • Deployed on Render with Docker, using small models (MiniLM + TinyBERT) to fit free-tier memory limits.
